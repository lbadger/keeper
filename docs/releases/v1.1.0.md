# Keeper v1.1.0

This release adds ZFS stream exports for recovery on a different machine and
shorter backup IDs.

## Changes

- New backups use seven-character, case-sensitive IDs such as `7aQm3Kx`, excluding
  the easily confused characters `0`, `O`, `I`, and lowercase `l`. Generation checks
  for collisions against available media metadata and inventories. Keep a shared
  `--inventory` to include offline cartridges in those checks.
- `zfs-restore --backup ID --output FILE` streams one backup into a file without
  ZFS installed. Keeper verifies tape checksums and completion in one pass, then
  publishes the file without overwriting an existing path. Receive it later with
  `zfs receive -u POOL/DATASET < FILE`. Atomic publication requires a filesystem
  supporting hard links.
- `zfs-restore --backup ID --stdout` emits the original send stream on stdout for
  piping to another command, with diagnostics kept separate. A later failure can
  leave partial output; use `pipefail` and check the result before using the
  received dataset.

```bash
# Save a stream for later recovery.
./keeper zfs-restore --backup 7aQm3Kx --output snapshot.zfs

# Or pipe it directly to another ZFS machine.
set -o pipefail
./keeper zfs-restore --backup 7aQm3Kx --stdout | \
  ssh recovery-host zfs receive -u tank/recovered
```

Both export modes take one explicit backup ID. Export full and incremental
backups separately, then receive them in order. Raw encrypted streams stay
encrypted. Exporting does not extract the snapshot's files.

## Compatibility and validation

Existing 32-character backup IDs remain supported, including mixed chains with
new incrementals and existing restore history. Cartridge IDs remain 32 characters.
Use v1.1.0 or newer to read backups with seven-character IDs; older executables
require the old ID format. Keeper's tape framing and SSH source protocol remain
unchanged.

Automated tests cover ID collisions, legacy chains, exact-byte exports across
multiple cartridges, missing completion markers, corrupted frames, cancellation,
existing-file protection, and broken pipes. Real ZFS receive tests require the
optional dedicated scratch pool; physical-drive qualification remains separate
from file-backed media and simulator testing.

See the [README](https://github.com/lbadger/keeper/blob/v1.1.0/README.md) and
[reference guide](https://github.com/lbadger/keeper/blob/v1.1.0/docs/reference.md)
for installation, recovery commands, and limitations.
